# 메모리·BufferStuffing 추가 조사 — 2026-09-10

## 결론

같은 입력으로 미리보기↔전체 화면을 20회 반복했을 때 초기 메모리 증가의 대부분은 **GL 그래픽 메모리**였습니다. 약 6~8회 이후 비슷한 범위에서 안정됐고, 화면 객체와 네이티브 할당량의 지속 누적은 확인하지 못했습니다. 무한 누수로 확정할 근거는 없으나 유지되는 그래픽 메모리는 크며 최적화 조사 대상입니다.

BufferStuffing 구간도 실제 표시 간격은 일정했습니다. 지속적인 프레임 끊김보다 약 한 표시 주기(이 기기에서 8.33ms)의 추가 파이프라인 지연과 부합합니다. 이는 입력부터 화면까지의 직접 측정값이 아닙니다.

## 방법

- Galaxy SM-M336K / Android 16, 기존 1.0.6 (24), main 06f8847 APK. 재빌드·설치 없이 측정.
- 영어/Montserrat, `Welcome to LED POP!`와 `by Sunny` 두 줄, 크기 50·속도 30·자간 24 유지. 효과·품질·주사율 변경 없음.
- force-stop 후 앱 시작, 10초 대기, 전체 화면 왕복 20회. 각 화면 UI 구조 확인 후 2초 대기해 dumpsys meminfo 수집. 이후 미리보기 60초, 30초 프레임 추적, 백그라운드 30초와 복귀 비교.
- 전체 과정 PID 27812 유지. 기존 30초×6 Perfetto 기록을 재분석하고 새 warm preview 30초를 추가. 앱 surface token을 display token으로 SurfaceFlinger 실제 표시 종료 시각에 연결.
- 테스트 중 광고 재생/클릭, 데이터 초기화, 강제 GC, 캐시 삭제는 실행하지 않았습니다. 마지막 입력과 앱 화면 복원 확인.

20회 복귀 시 기준 대비 PSS +329.81MiB, GL +325.17MiB로 증가분 대부분이 그래픽 항목과 대응합니다. Native allocated는 +2.82MiB입니다. 네이티브 resident PSS 감소에는 swap이 섞여 있으므로 이를 객체 해제량으로 해석하지 않습니다.

전체 화면의 EGL은 대체로 82.22MiB이고 복귀 때 18.14MiB로 반환됐습니다. Views/ViewRootImpl은 시작 337/1, 전환 직후 347/2, 대기 후 다시 337/1. Activity 1, WebView 3으로 누적되지 않았습니다.

소스에서 전체 화면 Canvas가 Modal 수명에 따라 생성되고, picture shader를 만드는 `useTilePicture`/`recordTile` 경로 및 Skia OpenGL 컨텍스트를 확인했습니다. SDK의 창 소멸자는 surface/window를 해제하며 실제 EGL 반환과 일치합니다. GL의 초기 증가 후 평탄화/백그라운드 부분 반환은 그래픽 캐시·드라이버 리소스 보유와 부합합니다. **개별 GL 할당의 소유자, 캐시의 정확한 한도, 특정 함수의 누수 여부는 현재 release 측정으로 확정하지 못했습니다.** 다국어 순회 없이도 재현돼 폰트 언어 변경만이 원인은 아닙니다.

[Perfetto 공식 설명](https://perfetto.dev/docs/data-sources/frametimeline) 역시 이 분류를 끊김과 구분되는 추가 버퍼 지연 상태로 설명합니다.

## 조치 판단과 한계

1. 그래픽 메모리 보유량을 낮출 수 있는지 먼저 검증할 가치가 있습니다. 다음 구현 실험은 동일 내용의 picture/shader 재생성·재사용과 Skia/드라이버 캐시 할당 추적입니다. 현재 증거만으로 임의 캐시 축소나 객체 강제 dispose를 넣지 않았습니다.
2. BufferStuffing은 프레임 예약/표시 경계의 후속 최적화 대상입니다. 프레임 제한, 고정 지연, 효과 해상도 축소를 넣지 않았습니다. 코드 원인을 확정하려면 frame scheduling/렌더러의 상세 추적 및 변경 전후 비교가 필요합니다.
3. 현재 결과는 이 기기의 동일 입력 20회와 안정 재생 7개 구간에 대한 조사입니다. 장시간·저메모리 기기·다른 효과·iOS 누수 부재를 보증하지 않습니다. 새 profiling APK는 생성하지 않았습니다.

최초 추가 조사 단계에서는 앱 소스 변경 없이 증빙과 문서만 추가했습니다. 이전 QA의 광고 만료 방어 수정과 별도 RootLayout 수정은 그대로 보존했습니다. 컴파일·커밋·푸시 없음.

증빙: [원본 측정/재현 스크립트](../artifacts/qa-memory-20260910/), `memory.json`, `memory-details.json`, `presentation-summary.json`, `warm-preview.pftrace`, `restored.xml`.

## 후속 최소 개선 — 소스 적용

- `buildCanvas.ts`를 Hook인 `useMarqueeCanvasProps.ts`로 변경하고 `useTilePicture` 호출을 preview/fullscreen 상위 컴포넌트로 이동했습니다. Modal 내부 Canvas가 다시 마운트돼도 상위 화면이 유지되고 입력이 같으면 동일 picture/paint를 재사용합니다. 미리보기와 전체 화면은 각자 최신 리소스 한 세트를 보유하며 전역 다중 캐시를 추가하지 않았습니다.
- 기존 useMemo 의존성을 유지해 텍스트·폰트·레이아웃·색·Pixel/Glow 설정 변경 시 재생성합니다. 셰이더 입력, 렌더 해상도, 이동 속도, 효과와 프레임 상한은 변경하지 않았습니다. 화면용 native surface는 기존 Modal 수명대로 동작합니다.
- `onSkiaCanvasLayout` 콜백을 안정화하고 너비/높이가 같으면 이전 상태를 반환합니다. 중복 레이아웃 이벤트로 인한 React 갱신을 줄이는 변경이며 SDK frame scheduling 자체를 바꾼 것은 아닙니다.
- `node --test scripts/qa-marquee-resources.cjs`: 4개 통과. 동일 입력 20회 재렌더의 picture/paint 각 1회 생성, 입력 변경 시 교체, Pixel/Glow 파라미터, 두 화면의 독립 소유를 검증했습니다. SDK 리소스 생성은 테스트 경계에서 대역을 사용하므로 GPU 메모리/화질 검증이 아닙니다.
- 새 APK 빌드·실기기 A/B 비교는 아직 수행하지 않았습니다. 메모리 감소량과 BufferStuffing 해소를 주장하지 않습니다. SDK 프레임 예약 변경은 원인·효과를 검증할 별도 실기기 비교가 필요해 보류했습니다. 기존 APK에는 이번 소스 변경이 없습니다. 컴파일·린트·커밋·푸시 없음.

## main 전달 범위

사용자의 후속 요청으로 QA 문서, 광고 표시 직전 만료/준비 상태 재확인, 화면 수명의 picture/paint 재사용, 동일 크기 레이아웃 갱신 억제, 회귀 테스트 파일을 main 커밋·푸시 대상으로 정리했습니다. 위의 커밋·푸시 미실행 문구는 각 조사/구현 시점의 기록입니다. 별도 RootLayout 스플래시 수정은 전달에서 제외하고 로컬에 보존합니다. 원본 측정 파일은 artifacts 아래 로컬에 남아 있으며 Git 전달에는 보고서와 테스트 소스가 포함됩니다. 후속 소스의 새 APK 빌드와 실기기 A/B 비교는 여전히 미실행입니다.
